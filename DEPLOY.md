# Deploying JobPilot

Render runs the API, the background workers and Postgres (with pgvector); Vercel runs the Next.js web app. The browser
only talks to the web origin: `/api/*` is proxied to the API, so the session cookie is first-party.

`render.yaml` is the **free tier**: one API instance that also runs the agents and the scheduler, and a free Postgres,
both in Singapore. It costs nothing, but the API sleeps after 15 minutes without traffic (about a minute to wake on
the next visit), scheduled runs don't fire while it sleeps, and Render deletes free databases after 30 days. To stay
always-on, switch the API to Starter and the database to the smallest paid plan in the Render dashboard (about
$14 a month). For launch traffic, replace `render.yaml` with `render.production.yaml` (2 API and 2 worker Standard
instances and a 1 GB database, roughly $120 a month).

The two services need each other's address, so deploy in this order: Render first (you get the API address), then
Vercel (you get the web address), then put the web address back into Render.

## 1. Push the code to GitHub

```bash
git init && git add -A && git commit -m "JobPilot"
git remote add origin git@github.com:<you>/jobpilot.git && git push -u origin main
```

`backend/.env` is git-ignored. Keep it that way: production secrets live in Render, not in the repo.

## 2. Generate the two secrets you set yourself

```bash
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"   # ENCRYPTION_KEY
```

`JWT_SECRET` is generated by Render. **Never change `ENCRYPTION_KEY` once users have connected their mail**: their saved
mail passwords can't be decrypted with a new key (they would have to reconnect).

## 3. Render: API, workers, database

1. Render → **New → Blueprint** → pick the repo. It reads `render.yaml`.
2. Fill in the `jobpilot-shared` environment group:

| Variable | Value |
|---|---|
| `ENCRYPTION_KEY` | from step 2 |
| `APP_URL` | your web origin, e.g. `https://jobpilot.app` |
| `CORS_ORIGINS` | the same origin |
| `ADMIN_EMAILS` | your account email (opens `/admin`) |
| `GROQ_API_KEY` | from console.groq.com (or set `LLM_PROVIDER=anthropic` and `ANTHROPIC_API_KEY`) |
| `ADZUNA_APP_ID` / `ADZUNA_APP_KEY` | developer.adzuna.com (free) |
| `JSEARCH_API_KEY` | RapidAPI JSearch (free tier: 200 requests/month for the whole service) |
| `HUNTER_API_KEY` | hunter.io (optional: real company contacts) |
| `SMTP_HOST` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` | a transactional provider for **system** mail (Resend, Postmark, SES). Applications never use this. |
| `SENTRY_DSN` | optional error reporting |
| `GITHUB_TOKEN` | a fine-grained token with no scopes (public data only): raises the proof-pack rate limit |
| `WHATSAPP_*` | see "WhatsApp digest" below (optional) |
| `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` | optional LLM tracing |

   For now set `APP_URL` and `CORS_ORIGINS` to the address Vercel will give you, `https://<project>.vercel.app`
   (you can correct them after step 4).
3. Deploy. On the free tier the API migrates the database when it boots (`RUN_MIGRATIONS=true`); the production
   blueprint uses `preDeployCommand: alembic upgrade head` instead, once per deploy. The API refuses to start in production with a default `JWT_SECRET`, no `ENCRYPTION_KEY`, insecure cookies
   or localhost CORS. That's on purpose, so read the deploy log if it doesn't come up.
4. Check `https://<api>.onrender.com/ready` returns `{"status": "ready"}`.

## 4. Vercel: web

1. Vercel → **Add New → Project** → the repo, root directory `frontend`.
2. Environment variable `API_URL=https://<api>.onrender.com`. Rewrites are resolved at build time, so redeploy after
   changing it.
3. Add your domain, and make sure `APP_URL` / `CORS_ORIGINS` on Render match it exactly.
4. Optional web variables: `NEXT_PUBLIC_CONTACT_EMAIL`, `NEXT_PUBLIC_GRIEVANCE_OFFICER` and `NEXT_PUBLIC_GRIEVANCE_EMAIL`
   (a real, monitored inbox: shown on `/trust`, `/privacy` and `/terms`). They're baked in at build time, so redeploy
   after changing them.

## Custom domain

The web app is the only public origin (the API is reached through the `/api` rewrite), so moving to your own domain
touches Vercel and two Render variables. Nothing in the code names a domain.

1. Vercel → Project → **Settings → Domains** → add `jobpilot.example` (and `www.` if you want it), set the DNS records
   Vercel shows, and make the new domain **primary**. Redirect the `*.vercel.app` address to it.
2. Render → `jobpilot-shared` group: `APP_URL=https://jobpilot.example` and
   `CORS_ORIGINS=https://jobpilot.example,https://<project>.vercel.app` (keep the old origin listed until the switch
   is done; it's comma-separated). The API redeploys.
3. Canonical URLs, `robots.txt` and `sitemap.xml` follow Vercel's production domain automatically. To pin them, set
   `NEXT_PUBLIC_SITE_URL=https://jobpilot.example` on Vercel and redeploy.
4. Session cookies belong to the origin, so users sign in once more on the new domain. Password-reset links use
   `APP_URL`, so old links in inboxes keep pointing at the old address until they expire.
5. Unchanged: the WhatsApp webhook and the Chrome extension talk to the API's own address, not the web domain.

## 5. First-run checklist

- [ ] Register your account on the live site, then open `/admin`. It works if `ADMIN_EMAILS` has your email.
- [ ] Create the showcase account for demo visitors: register `demo@example.com` (or set `DEMO_TEMPLATE_EMAIL`), upload
      a strong sample resume, run the agents once. Demo visitors get a private copy of it.
- [ ] Settings → **Your email**: connect your Gmail with an app password and approve one draft to yourself.
- [ ] Forgot password → the reset email arrives from `SMTP_FROM`.
- [ ] `/admin` → **Shared ingestion** shows every source with a recent last fetch and nothing failing.

## Gmail sending with Google sign-in (recommended)

Students connect Gmail by signing in with Google instead of pasting an app password. JobPilot asks only for
`gmail.send` (send as the user, no reading) plus `openid email` (which address was connected).

1. Google Cloud Console → create a project → **APIs & Services → Library** → enable the **Gmail API**.
2. **OAuth consent screen**: External; app name JobPilot; support email and developer contact; app domain = your web
   origin, privacy policy `https://<web>/privacy`, terms `https://<web>/terms`. Scopes: `openid`, `.../auth/userinfo.email`,
   `.../auth/gmail.send`. While the app is in *Testing*, add your testers' Gmail addresses (up to 100).
3. **Credentials → Create credentials → OAuth client ID** → Web application. Authorized redirect URI:
   `https://<your web origin>/api/mail/google/callback` (it must match `APP_URL` exactly, through the Vercel proxy).
4. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in the Render `jobpilot-shared` group. Settings → Your email then
   shows **Connect Gmail with Google**; app passwords stay available for other providers.
5. Before going beyond 100 test users, submit the app for **verification**. `gmail.send` is a *sensitive* scope, not a
   *restricted* one, so Google reviews the app (demo video, privacy policy) but no third-party security assessment is
   needed. Don't add read scopes: they're restricted and would require that assessment.

Sends from one mailbox are spaced at least `SEND_SPACING_S` (90) seconds apart, and every application email ends
with an opt-out line ("reply no and I won't follow up").

## WhatsApp digest (optional)

1. Meta for Developers → create an app → add **WhatsApp** → note the **Phone number ID** and create a permanent
   **System user access token** with `whatsapp_business_messaging`.
2. WhatsApp Manager → **Message templates** → create a *Utility* template named `jobpilot_daily_digest` with a body of
   two parameters, for example: `Hi {{1}}, {{2}}`. Wait for approval.
3. Set `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_TEMPLATE=jobpilot_daily_digest`, `WHATSAPP_TEMPLATE_LANG=en`,
   `WHATSAPP_APP_SECRET` (App settings → Basic) and a random `WHATSAPP_VERIFY_TOKEN`.
4. Webhook: callback `https://<api>/api/whatsapp/webhook`, verify token as above, subscribe to `messages`.
   Replies of STOP withdraw that student's consent automatically.

### WhatsApp approvals (optional)

5. Create a second *Utility* template, e.g. `jobpilot_approval`, with a body of three parameters,
   `{{1}} at {{2}} is ready to send. Worth sending: {{3}}`, and three **quick reply** buttons in this order:
   `Approve`, `Edit in app`, `Skip`. Add Hindi (`hi`) and Marathi (`mr`) versions of both templates if you want them.
6. Set `WHATSAPP_APPROVAL_TEMPLATE=jobpilot_approval` and `WHATSAPP_TEMPLATE_LANGS=en,hi,mr` (only the languages you
   got approved). The morning digest is then followed by the 3-5 best drafts with buttons. Each button is signed for
   that student, expires in 24 hours and stops working if they sign out everywhere. Approving uses the same daily
   quota and scam block as the web, and is recorded with channel `whatsapp`. Retries from Meta are ignored by message id.

## Chrome extension

Load `extension/` unpacked for testing (see `extension/README.md`). To publish it, zip the folder for the Chrome Web
Store and set its default API address to your API's URL. Users create their token in Settings → Chrome extension.

## Colleges

On `/admin` → **Colleges**: create a college (you get an invite code) and make its placement officer an officer (they
need an account). Students join with the code in **Campus**; the officer gets the **College** dashboard.

## Scaling

| Signal (on `/admin`) | Action |
|---|---|
| Agent queue "Queued" keeps growing | More worker instances, or raise `WORKER_CONCURRENCY` |
| Ingestion "Overdue" targets > 0 | More worker instances (each fetches `INGEST_MAX_TARGETS_PER_TICK` per minute) |
| API p95 rising | More API instances or `WEB_CONCURRENCY` |
| Postgres connections near the limit | Each process opens up to `DB_POOL_SIZE + DB_MAX_OVERFLOW` (5 + 10); keep `processes × 15` under `max_connections`, or add PgBouncer |
| AI spend per active user rising | Lower `LLM_SCORE_TOP_K`, or the Free plan's `llm_usd_per_day` in `app/config.py` |

Workers and API instances are stateless. Runs and ingestion targets are claimed with `FOR UPDATE SKIP LOCKED`,
the schedulers take advisory locks, and live updates fan out through Postgres `LISTEN/NOTIFY`. So any number of
replicas is safe, with no Redis needed.

## Rotating keys

- **Groq / Adzuna / JSearch / Hunter / SMTP**: change the value in the Render group; the services redeploy.
- **JWT_SECRET**: changing it signs everyone out (harmless).
- **ENCRYPTION_KEY**: don't, unless it leaked. Users then reconnect their mail in Settings.

## Payments with Razorpay (optional)

Pro (₹199/month by UPI AutoPay or card) and the Week Pass (₹49, 7 days) run on Razorpay's hosted pages, so no card or
UPI details reach JobPilot. Until the keys are set, Settings shows "Request Pro" and admins switch Pro on by hand.

1. Razorpay Dashboard → **Subscriptions → Plans** → create a monthly plan of ₹199. Note its `plan_...` id.
2. **Settings → API keys**: generate a key pair. **Settings → Webhooks**: URL `https://<api>/api/payments/webhook`,
   a secret, and the events `payment_link.paid`, `subscription.activated`, `subscription.charged`,
   `subscription.cancelled`, `subscription.halted`, `subscription.completed`, `payment.failed`.
3. Set `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` and `RAZORPAY_PRO_PLAN_ID` on Render.
   Start with test-mode keys and pay with Razorpay's test UPI/cards, then switch to live keys.
4. Invoices: set `SELLER_NAME`, `SELLER_ADDRESS` and, once GST-registered, `SELLER_GSTIN` and `SELLER_STATE_CODE`.
   With a GSTIN invoices are tax invoices with 18% GST inside the price (CGST + SGST); without one they're receipts.
   Have your accountant check the invoice format before going live.
5. The "₹99 on first interview" outcome plan is off (`OUTCOME_PLAN_ENABLED=false`) until you decide to offer it.

Plans change only on verified webhooks, each event applied once. Cancelling keeps Pro until the paid period ends.

## Forwarded job-alert emails (optional)

Students forward Internshala, Unstop or Naukri alert emails to `alerts+<token>@<INBOUND_EMAIL_DOMAIN>`; JobPilot keeps
the job links (it never opens those sites). Any inbound-mail service that POSTs the message as JSON or form data works
(Postmark Inbound, SendGrid Inbound Parse, Mailgun Routes, Cloudflare Email Workers):

1. Point the domain's MX records at the provider and route `alerts+*@` to
   `https://<api>/api/inbound/email?secret=<INBOUND_EMAIL_SECRET>`.
2. Set `INBOUND_EMAIL_DOMAIN` and a random `INBOUND_EMAIL_SECRET` in the Render group. Settings then shows each student
   their address.

## Proof Link signing key (optional)

Proof Links are signed with Ed25519. Without `PROOF_SIGNING_KEY` the key is derived from `ENCRYPTION_KEY`, which is
already stable, so links keep verifying across deploys. To use a dedicated key, generate one and set it on Render:

```bash
python3 -c "import os,base64; print(base64.urlsafe_b64encode(os.urandom(32)).decode().rstrip('='))"
```

Changing the key later makes earlier links fail verification, so set it once.

## Privacy operations (DPDP)

- **Rights requests and grievances** arrive in `/admin` → Privacy requests, with the 30-day reply date. Answering one
  emails the reply from `SMTP_FROM`.
- **Inactive accounts**: the daily retention sweep emails a notice to accounts unused for 11 months and deletes them at
  12 (`INACTIVE_DELETE_DAYS`, `INACTIVE_NOTICE_DAYS`). Signing in cancels it.
- **Age gate**: sign-up requires "I am 18 or older"; older accounts confirm once in-app and their agents pause until they do.
- **Consent notice**: change the text in `backend/app/services/consent.py` and bump `CONSENT_VERSION`.
- **Breach**: follow [docs/breach-response.md](docs/breach-response.md) (72-hour report to the Data Protection Board).

## Campus data and row-level security

Officer views of individual students run inside an "officer context" where Postgres row-level security hides every
student without an active `college_share` consent. Migration 0019 enables and forces RLS on `profiles`,
`job_matches` and `drive_statuses`, and creates a read-only `jobpilot_officer` role when the database user may create
roles. Where it can't, FORCE still applies the policy to the app's own (non-superuser) role, which is the case on
Render. If a later migration adds a table that officer queries read, also `GRANT SELECT` on it to `jobpilot_officer`.
Every officer view writes an `audit_events` row (`tpo_view`).

## Backups and data requests

Render Postgres takes daily backups (point-in-time recovery on paid plans). Users export or delete their own data in
Settings → **Your data**. Deleting an account removes every row that belongs to it.
